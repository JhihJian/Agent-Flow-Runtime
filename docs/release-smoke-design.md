# 发布级冒烟门禁设计

## 目的

发布级冒烟门禁验证运行时最容易影响交付的三条状态链路：完整流程能否走到结束、并行结果冲突能否阻止错误汇合、进程中断后能否从持久化事实恢复。门禁面向发布前的可重复检查，测试名称和入口固定，失败时应能直接定位到主链路、冲突处理或恢复语义。

门禁由 `test:smoke` 统一运行：

```bash
npm run test:smoke
```

发布命令按以下顺序执行完整检查：

```bash
npm run test:release
```

`test:release` 依次运行 `check`、`build`、离线发布级冒烟门禁和现有 `npm test`。现有单元测试失败时，发布命令必须失败；相关测试迁移由主线维护者负责完成。

## 三类流程覆盖

### 1. 完整主链路

`test/release-flow-smoke.test.ts` 使用发布级父 Flow 和子 Flow，覆盖以下顺序：

1. Agent 节点读取初始变量并提交结果。
2. 命令节点接收上一步结果，输出内容和变量。
3. 两个并行分支分别执行检查。
4. 汇合节点接收两个分支结果。
5. 父 Flow 执行子 Flow，向子 Flow 传递任务和父侧变量。
6. 子 Flow 返回结果，父 Flow 完成。
7. 读取保存后的 JSON，确认终态、变量、节点记录、子 Run 和并行轮次都能重新恢复。

验收重点是结果路由、全局变量覆盖、下一跳变量隔离、并行汇合、子 Flow 显式输入与回传，以及持久化快照与内存终态一致。命令的业务变量和执行证据也必须分别可验证。

### 2. 并行冲突

`test/release-flow-conflict.test.ts` 让两个并行分支写入同名全局变量，分别覆盖不同值和相同值两种情况。冲突必须产生确定的 `variable_conflict` 失败事实，并满足以下条件：

- Run 进入 `failed`，错误摘要包含冲突变量名。
- 冲突变量不会覆盖最终 Run 变量中的原值。
- 汇合命令不会执行。
- 两个分支的结果和执行记录都完整保存，分支执行顺序不会改变冲突结论。

该用例保护并行合并的门禁语义，避免最后写入值覆盖冲突而形成看似成功的发布结果。

### 3. 中断恢复

`test/release-flow-recovery.test.ts` 验证运行事实写入 JSON 后，在 Agent 节点或命令节点边界发生中断，重新创建协调器仍能恢复到可审计的结果。用例应覆盖：

- 已完成节点不重复执行。
- 被中断的 Agent 节点创建关联的新尝试，并继续沿正确结果边路由。
- 未完成命令不被无条件重放；其事实按运行时恢复语义进入失败或人工处理状态。
- 恢复后的 Run、NodeRun、变量和序号来自 JSON 持久化内容，最终状态可再次读取。

当前恢复冒烟包含两个独立场景：中断 Agent 会创建带 `retryOf` 的新访问并继续完成；中断命令直接失败且执行器调用次数为零，证明外部副作用没有被自动重放。

恢复测试必须检查执行次数或命令记录，防止测试只验证最终状态而遗漏重复副作用。

## 测试替身和真实边界

离线门禁采用确定性 Agent 替身。替身按提示内容和节点引用返回固定结果、消息和变量，不访问模型、网络、Pi 会话或 provider。这样每次运行都能得到相同的节点路径，并能把失败归因到运行时状态机。

命令节点使用发布级夹具声明的真实命令入口和真实参数传递链路。命令的标准输出按运行时约定解析为内容和变量，退出码与标准错误参与成功或失败判断。命令脚本只负责构造可重复的测试输入，不模拟 Agent，也不绕过协调器。

持久化使用真实 `JsonFileRunStore` 和临时目录中的 JSON 文件。测试必须经过文件写入、重新创建 Store、读取快照这条路径，不能用内存 Store 替代主链路的持久化断言。冲突用例可以使用 `InMemoryRunStore` 聚焦合并失败，但恢复和完整主链路必须保留 JSON 文件验证。

离线门禁的覆盖边界到这里为止。真实 Pi CLI、真实 Pi SDK 会话、认证配置、模型调用、provider 连接和网络行为属于 `test:integration`，由 `npm run test:integration` 负责。离线冒烟不能通过注入真实 provider 来扩大覆盖，也不能把 provider 不可用误报为运行时逻辑失败。

## 门禁维护规则

1. `test:smoke` 只列出三条发布级用例，新增流程语义时先判断属于主链路、冲突还是恢复；只有形成发布风险覆盖时才加入该门禁。
2. 修改 Flow 状态、变量合并、子 Flow、命令执行、RunStore 或恢复语义时，必须同步检查对应类别的测试和本文档；若验收边界变化，也要更新 `test:integration` 的职责说明。
3. 测试替身的输入、输出和调用次数必须确定。禁止依赖当前时间、随机数、网络、用户目录中的认证文件或本机已有运行记录。
4. 每条冒烟用例都要验证可观察事实，而不只验证 `completed` 或 `failed`。至少包括关键变量、执行顺序或次数、错误类别、持久化快照和恢复后的状态中的适用项。
5. 发布夹具保持最小化。命令、父 Flow、子 Flow 和冲突 Flow 只保留验证门禁所需的节点；改变夹具结构时，要说明它新增的状态覆盖。
6. `test:release` 是发布前唯一推荐入口。维护者不得用单独的 `test:smoke` 结果替代 `check`、`build` 或现有 `npm test`。
7. 发现现有 `npm test` 与发布门禁的职责重叠或失败时，修复测试归属和实现，再保持 `test:release` 的顺序不变，避免通过删除检查来降低门槛。

## 失败定位

- 主链路失败：先看 Agent 结果、命令输出变量、并行轮次和 child Run 记录。
- 冲突失败：先看两个分支的变量差异、`variable_conflict` 错误和汇合命令调用记录。
- 恢复失败：先看 JSON 文件中的最后一次保存、NodeRun 状态、关联尝试和实际执行次数。
- 只有真实 Pi 或 provider 连接失败时，才转到 `test:integration` 的环境、认证和会话日志排查。
