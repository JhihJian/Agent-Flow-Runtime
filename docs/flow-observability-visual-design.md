# Flow 运行记录可视化设计

## 1. 设计定位

目标读者是需要快速确认运行结果、持续跟进进行中任务，或排查失败与恢复原因的开发者、Agent 操作者和维护人员。

这是面向一次具体 Run 的运行记录阅读界面，首要回答四个问题：

1. 这次 Run 执行的是什么 Task，使用了哪个 Flow 版本？
2. 当前或最终处于什么状态，最后停在哪里？
3. 为什么从一个节点进入下一个节点？
4. 哪些节点访问、并行分支、错误和恢复事实可以继续追溯？

核心原则是：**时间线展示事实，流程图解释结构，详情面板承载证据。** 三者互相定位，分别承担执行顺序、路径背景和依据追溯。

## 2. 总体结构

展示由两个主要视图组成：

```text
运行中心
  -> 近期 Run 列表
  -> 选择一个 Run

Run 详情
  -> 身份和状态摘要
  -> 实际执行时间线
  -> 并行轮次和访问关系
  -> 选中事实的详情与依据
```

运行中心解决“找哪一次”，Run 详情解决“这一次发生了什么”。不把所有运行都画在同一张流程图里，也不把一次 Run 拆成互不关联的节点、路由和并行三个列表。

## 3. 运行中心

### 3.1 列表目标

列表用于扫描和比较，不用于展示完整历史。默认按最近一次状态变化或开始时间倒序排列，优先让用户找到正在运行、失败或刚刚中断的 Run。

每行的信息顺序为：

| 优先级 | 信息 | 展示方式 |
| --- | --- | --- |
| 1 | Task | 一行摘要，过长截断 |
| 2 | Flow | 名称或 `flowId`，附版本短标识 |
| 3 | 状态 | 用户化主状态，例如“执行中”“已失败” |
| 4 | 位置 | 当前节点、等待中的并行分支或最后位置 |
| 5 | 时间 | 最近更新、开始时间、持续时间或完成时间 |
| 6 | 风险 | 错误类别、恢复次数、历史是否完整 |
| 7 | 标识 | Run ID 作为次级信息，可复制 |

`status` 和 `phase` 不合并成一个内部枚举。界面显示一个易读的主状态和一条解释性阶段描述，例如：

```text
执行中
正在等待 1 个并行分支
```

而不是直接显示：

```text
running / waiting_parallel
```

### 3.2 筛选和选择

首屏提供轻量筛选：

- 全部
- 执行中
- 失败或中断
- 已完成
- 有恢复记录

列表行支持按 Flow、状态、时间和错误类别进一步缩小范围。选择一行后进入详情，列表不展开长文本，也不默认显示会话引用、完整版本指纹、Prompt 或命令输出。

`historyCompleteness = legacy` 的 Run 在列表中显示“历史不完整”标识。它仍然可以查看，但不能用缺失事实推断未执行节点，也不应与完整历史进行无提示比较。

### 3.3 比较

比较只允许默认对齐 `flowId + flowVersion` 相同的 Run。横向比较以下指标：

- 总耗时
- NodeRun 访问次数
- 实际访问路径
- 返工或循环次数
- ParallelRound 数量和分支耗时
- 失败节点与错误类别
- 恢复次数和最终状态

Flow 版本不同的 Run 必须保留明显的版本差异提示。跨版本只能比较通用 Run 指标，不能把同名节点直接当作同一个位置。

## 4. Run 详情首屏

详情首屏从上到下分为四层。

### 4.1 身份层

顶部固定显示：

```text
Task 摘要
Flow 名称 / flowId       Flow 版本短标识
Run ID                   历史完整性
```

Task 摘要是主标题，Flow 是上下文。不要让 Run ID 或静态 Flow 名称成为首要视觉焦点。

### 4.2 状态层

状态层突出当前或最终情况：

```text
已失败
结果校验失败
最后位置：验证 #2
开始 10:24:18    结束 10:27:03    耗时 2 分 45 秒
事实水位：23     最后同步：刚刚
实时连接：已连接
```

状态、阶段、最后位置和实时连接必须分开：

- Run 状态说明执行生命周期。
- 阶段说明正在执行、路由、等待并行或已停止。
- 最后位置保留终态 Run 的上下文，即使当前定位为 `none`。
- 实时连接只说明页面是否还能接收通知，不能说明 Run 是否停止。

### 4.3 摘要层

使用少量平铺指标帮助用户判断复杂度：

- 实际节点访问次数
- 不同节点数量
- 返工/循环次数
- 并行轮次数
- 失败或中断次数
- 恢复次数

这里不使用一组装饰性卡片堆满页面。指标应服务于扫描和比较，异常指标才需要强调。

### 4.4 主内容入口

首屏默认打开“执行时间线”，并在旁边提供两个次级入口：

- 结构视图：查看 Flow 版本对应的静态拓扑和实际走过的边。
- 依据视图：查看当前选中 NodeRun 的受权限控制证据。

时间线是默认主视图，因为它最能表达实际发生顺序和因果关系。

## 5. 执行时间线

### 5.1 混合事实

时间线按 Run 内 `sequence` 排列所有事实，不把 NodeRun、RouteDecision、ParallelRound 和恢复记录拆成四条独立列表。

建议的节点形态：

```text
01  Run 开始
02  节点开始       分析 #1
03  节点完成       结果：已分析
04  路由选择       已分析 -> 修改
05  节点开始       修改 #1
06  节点完成       结果：需要返工
07  路由选择       需要返工 -> 分析
08  节点开始       分析 #2
...
```

每一行都显示序号、事实类型、可读名称和状态。点击后在详情区域打开对应事实，且不会跳离当前 Run。

### 5.2 返工和循环

同一个 `nodeRef` 的访问必须显示访问次数和 NodeRun ID 的短标识：

```text
验证 #1  已完成  -> 返工 -> 修改 #2
验证 #2  已完成  -> 通过
```

不可将多次访问折叠成一个“验证”节点状态。可以提供折叠显示，但折叠标题必须写明访问次数，并能展开每一个 NodeRun。

### 5.3 并行轮次

并行不是一行无法展开的“并行完成”标签，而是时间线中的复合事件：

```text
并行轮次 #1  执行中
  ├─ 测试       已完成
  ├─ 静态检查   执行中
  └─ 汇合       尚未开始
```

展开后显示分支泳道，每个分支包含节点访问、开始/结束时间、状态和结果。汇合 NodeRun 位于分支之后，并明确使用的是本轮分支结果。

相同 `parallelRef` 的不同轮次必须分开显示：

```text
并行轮次 #1  已失败
并行轮次 #2  已完成
```

不能按并行入口名称合并，否则会把返工前后的结果混在一起。

### 5.4 恢复

恢复是时间线中的独立事实，必须同时连接旧 NodeRun、新 NodeRun 和恢复策略：

```text
分析 #1       已中断
恢复          Agent 重试，来源：分析 #1
分析 #2       执行中
```

命令节点中断时显示：

```text
构建命令 #1   已中断
恢复决定     未自动重放，Run 进入失败/人工处理
```

恢复不能伪装成普通的节点开始，也不能覆盖旧访问。

## 6. 结构视图

结构视图展示指定 Flow 版本的静态拓扑，但只把它当作背景和定位工具。

- 已访问节点显示实际 NodeRun 访问次数和状态。
- 同一节点多次访问显示多个访问标记，而不是覆盖成一个状态。
- 已选择的边来自 RouteDecision，并显示结果名。
- 未访问节点保持中性，不表示失败，也不表示之后一定不会访问。
- 并行入口显示轮次标识，分支和汇合节点显示本轮关联。
- Flow 文件缺失、版本不匹配或历史为 legacy 时，结构视图显示“拓扑仅供参考”。

实际路径应当使用更强的视觉层级，静态未访问区域降低对比度，但不能隐藏到无法理解整体结构。结构视图不应抢过时间线成为首屏主视图。

## 7. 事实详情面板

点击时间线事实后，右侧或下方详情面板展示该事实的上下文。

### 7.1 NodeRun

```text
节点：验证
访问：#2
NodeRun ID：短标识，可复制
状态：已完成
动作：复用 Agent
进入来源：路由“需要返工”
所属并行轮次：无
恢复前驱：无

输入摘要
结果：通过
后续路由：结束

执行依据
Pi 会话：可用
交互范围：可用
完整依据：按权限查看
```

执行状态和业务结果分开显示。命令退出码非零时，应显示“命令执行完成，业务结果为失败”，不能直接显示成“节点崩溃”。

### 7.2 RouteDecision

路由详情只回答选择事实：

```text
来源：验证 #2
结果名：需要返工
目标：修改
选择序号：17
```

不要把结果名自动翻译成“业务通过”或“业务失败”。结果含义由 Flow 定义和后续路径共同表达。

### 7.3 ParallelRound

轮次详情显示：

- 并行入口和轮次编号
- 本轮共同输入摘要
- 每个分支对应的 NodeRun
- 分支状态和结果
- 汇合 NodeRun、汇合输入和汇合结果
- 轮次状态和失败原因

每个分支都必须能跳转到对应 NodeRun，不能只显示一组聚合数字。

### 7.4 Recovery

恢复详情显示：

- 被中断的 NodeRun
- 新建的 NodeRun（如有）
- 恢复策略
- 恢复时间和事实序号
- 恢复后是继续执行、失败还是等待人工处理

## 8. 状态、连接和异常表达

### 8.1 状态文案

用户看到的是解释性文案，内部枚举只作为高级信息：

| 内部状态 | 主文案 | 阶段示例 |
| --- | --- | --- |
| `running` | 执行中 | 正在执行节点、正在路由、正在等待并行 |
| `completed` | 已完成 | 已到达结束边 |
| `failed` | 已失败 | 节点执行异常、路由失败、结果校验失败 |
| `interrupted` | 已中断 | 进程中断，等待恢复或人工处理 |

颜色只作为辅助。状态必须同时有文字、图标或位置变化，不能只靠红绿颜色区分。

### 8.2 关键误解防止

- `running + executing_node` 不是节点成功，而是节点仍在执行。
- `running + routing` 不是停滞，而是正在根据结果选择去向。
- `running + waiting_parallel` 不是失败，应显示已完成和待等待的分支数量。
- NodeRun 已完成但命令结果为 failure，不等于执行器异常。
- Run 失败和页面断线是两件事，必须分别显示。
- 没有新事件不等于 Run 停止，页面应显示最后同步水位。
- 相同节点名称重复出现通常表示返工、循环或恢复，不是重复数据。

### 8.3 断线和重连

页面断线时保留最后确认的历史快照，并显示：

```text
实时连接已断开
最后同步：sequence 23
Run 仍可能继续执行，重连后将重新校正快照
```

重连后先读取新的历史快照，再接收更高序号事件。若发现序号跳跃，显示“断线期间存在未接收通知，已用快照校正”，不根据缺少的事件猜测中间路径。

## 9. 证据和隐私

默认可见：

- Task 摘要
- 节点输入摘要
- 结果名和结果摘要
- 错误类别与错误摘要
- 会话/交互引用是否可用
- 命令输出是否可查询

默认隐藏或按权限展开：

- 完整 Task 正文
- 完整 Prompt
- Agent 对话
- stdout 和 stderr
- 会话文件路径
- 完整 Flow 内容指纹

证据入口必须属于具体 NodeRun。不能提供脱离 Run 的全局会话查看，也不能因为用户打开了 Run 列表就加载所有敏感输出。

## 10. 空、加载和异常状态

- **没有运行记录**：说明当前没有可查看的 Run，并保留进入 Flow 的入口。
- **列表加载中**：保留表格结构骨架，避免页面跳动。
- **Run 不存在**：明确提示该 Run 已不存在或当前权限不可见。
- **历史不完整**：显示 legacy 提示，并说明不能据此推断缺失事实。
- **Flow 版本不可用**：仍展示历史时间线，把结构视图标记为仅供参考。
- **证据无权限**：保留状态、结果和引用，明确说明完整依据不可用，不显示空白假装没有证据。
- **实时连接失败**：保留快照和最后水位，提供重新同步入口，不改变 Run 状态。

## 11. 推荐阅读顺序

用户进入一个 Run 后，应能按以下顺序完成理解：

```text
身份和状态
  -> 当前/最后位置
  -> 实际时间线
  -> 为什么进入下一步
  -> 并行/返工/恢复关系
  -> 失败节点详情
  -> 受权限控制的完整证据
```

任何需要先打开静态 Flow 图、先阅读完整日志，或先理解内部枚举才能回答“现在发生了什么”的设计，都不符合本方案。

## 12. 关键取舍

- 主视图选择事实时间线，而不是静态流程图，因为排障依赖真实访问顺序。
- 运行列表选择密集表格，而不是大量状态卡片，因为用户需要比较和筛选。
- 并行使用可展开泳道，而不是把分支压成一个百分比，因为分支归属和汇合输入是事实。
- 返工和恢复保留多次访问，而不是合并节点，因为覆盖历史会破坏因果解释。
- 证据按需展开，而不是默认铺开，因为长文本和敏感输出不应阻塞首屏理解。
- 首版保持只读，不在观测页面放置重试、继续或停止按钮。控制行为需要独立的权限和运行控制契约。
