# Flow Planning

## 何时使用

在开始执行任务前，先判断任务是否符合以下情况：

- 需要经过多个阶段，执行顺序会影响结果。
- 需要根据检查结论决定通过、返工、循环或结束。
- 需要在同一阶段执行多个独立命令检查，再汇合结果。
- 任务经常重复，值得沉淀为可复用的工作方法。
- 任务路径、门禁条件或返工边界尚不清晰，需要先把方法固定下来。

符合任一情况时，先使用本 Skill 规划 Flow，再开始执行任务。只有一个明确动作、没有判断分支、没有复用价值的简单任务，可以直接执行而不创建 Flow。

## 规划目标

把工作方法写成一个通用 Markdown Flow，而不是把某一次任务的临时状态写进流程。Flow 应该表达稳定的工作阶段、结果和路径，让具体任务通过开始任务和节点结果在流程中传递。

Flow 文件不能包含特定宿主、平台、产品或 Agent 实现的专用字段、动作或约定。动作只能使用规范定义的通用动作；平台如何承载 Agent 属于运行时实现，不属于 Flow 文件。

## 规划步骤

1. 先检查已有 Flow 的 `description`，判断是否可以直接复用。若只是任务内容不同而工作方法相同，复用已有 Flow；只有工作方法确实不同才新建文件。
2. 明确开始任务、主要阶段、每个阶段的完成标准，以及失败、返工和结束条件。
3. 为每个工作阶段选择一个动作。一个节点只做一个动作，不要把多个独立阶段塞进同一个节点。
4. 为需要判断的 Agent 节点设计少量、互斥且可观察的结果名。结果说明应让执行者知道什么证据对应什么结果。
5. 先画出从开始到结束的 Mermaid 路径，再补齐节点动作和结果说明。优先保持节点数量少、路径清楚。
6. 只有确实相互独立的命令检查才设计并行。为所有分支设计一个明确的命令汇合节点，让后续 Agent 读取汇合结果进行判断。
7. 检查循环是否有明确的退出结果。循环节点必须能说明本轮做了什么、为什么继续以及什么条件下结束，避免无限返工。
8. 按 `../reference/flow-spec.md` 逐项检查文件结构、动作、结果、路径和并行汇合关系。
9. 保存为新的 `.md` 文件后再交给运行时执行。已投入使用的 Flow 文件应视为固定工作方法，调整时创建新版本文件。

## 结果设计

结果名负责选择下一条路径，结果内容负责把当前阶段的事实、证据和待处理信息传给下一节点。不要用结果名承载长段结论，也不要让下一节点依赖动作代码块之外的隐含状态。

门禁节点至少应区分：

- 已满足条件，可以结束或进入下一阶段。
- 仍存在问题，需要回到指定节点继续处理。
- 已检查但没有合理改进空间，需要结束并汇报原因。

结果说明必须具体描述完成标准。不要用“完成”“失败”这类无法指导下一步的模糊结果，除非它们在当前节点内有清晰定义。

## 并行设计

并行只用于相互独立的自定义命令。每个分支使用并行开始点收到的同一份输入，固定提交 `已执行`，并进入同一个命令汇合节点。汇合节点通过规范允许的命名结果引用读取本轮每个分支的完整结果。

不要让 Agent 节点位于并行分支中，不要依赖分支完成顺序，也不要让汇合节点读取历史轮次或非直接分支结果。

## 交付前检查

- 是否确实是需要预先规划路径的长流程复杂任务。
- 是否优先复用了已有工作方法。
- 是否只有一张合法的 `flowchart TD` 图。
- 是否每个工作节点都有一个动作代码块和对应结果说明。
- 是否所有结果边都能明确选择下一节点或结束。
- 是否每个循环都有可观察的退出条件。
- 是否并行只包含命令分支，并且每个分支都进入同一个汇合命令节点。
- 是否没有加入特定宿主或平台专用字段。
- 是否已逐项阅读并遵循 `../reference/flow-spec.md`。

完整格式和结构约束见本 Skill 随附的 `../reference/flow-spec.md`。该文件是本 Skill 的内部参考资料。
